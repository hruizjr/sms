# backend/

The Go backend: one Go module (`github.com/hruizjr/sms/backend`) that builds two executables, `api` and
`migrate` (ADR-0002, ADR-0003). Phase 3 is built in reviewed groups
([decision log §7](../docs/engineering/decision-log.md#7-owner-decisions--phase-3-walking-skeleton-2026-11-25)).

**Current state — Phase 3 Groups 1, 2, 4 and 6, and Phase 4 Group 1:** an HTTP API with configuration,
structured logging, `/healthz`, `/readyz` (which checks PostgreSQL), Prometheus metrics on a separate
loopback-only listener, graceful shutdown, a PostgreSQL connection pool, goose migrations, Go types and Chi
routes generated from the public API contract (not mounted in production; see
[OpenAPI code generation](#openapi-code-generation-public-api-v1)), unit and integration tests, CI, and a
container image for the local Docker Compose stack (Group 6).

**Phase 4 Group 1** ([decision log §18](../docs/engineering/decision-log.md#18-owner-decisions--database-role-separation-and-tenant-registry-phase-4-group-1-2026-11-26))
adds the database foundation: separate database roles for migrations (`sms_migrator`) and the API
(`sms_app`), with checks that refuse unsafe roles; the transaction-local tenant-context helper for
Row-Level Security; the platform-owned tenant registry (the `tenants` table, sqlc queries and the
`internal/tenancy` repository); and the RLS catalog guard in CI.

**Phase 4 Group 2** ([decision log §19](../docs/engineering/decision-log.md#19-owner-decisions--messaging-backend-and-provider-integration-foundation-phase-4-group-2-2026-11-27))
adds the working messaging backend: the public API v1 (`POST /v1/messages`, `GET /v1/messages`,
`GET /v1/messages/{message_id}`) with Bearer API keys, the `dispatcher` executable that hands messages to the
configured provider through the provider-independent interface, the **simulator** provider (the only one;
no real telco adapter, no SMS is ever sent), delivery receipts, and the local administration tool `smsctl`.
See [Messaging](#messaging-phase-4-group-2).

## How the API uses PostgreSQL

```
cmd/api ── config.Load ──▶ database.Open (pgxpool, lazy: no connection yet; every new connection
        │                    runs the application-role check, database.RequireApplicationRole)
        ── startup Ping (bounded by DB_CONNECT_TIMEOUT) ── unreachable: logged, not fatal
                                                         ── unsafe role: the API refuses to start
        ── httpserver.Run
              GET /healthz ──▶ 200 always while the process serves HTTP (no database check)
              GET /readyz  ──▶ listeners serving? ──▶ Ping (bounded: 2 s) ──▶ 200 ready | 503 problem
        ── SIGTERM: stop accepting → finish in-flight requests → close the pool
```

- **One pool per process**, created at startup and shared (AGENTS.md §7.5). Its size is bounded by
  `DB_MAX_CONNS`; requests beyond that wait for a free connection (bounded by their context).
- **Connections are established lazily.** The API starts even if PostgreSQL is down, reports `503` on
  `/readyz`, and recovers by itself when PostgreSQL becomes reachable. Invalid *configuration*, by contrast,
  stops the process at startup.
- **Each connection** has a bounded connect timeout (`DB_CONNECT_TIMEOUT`) and is recycled after
  `DB_MAX_CONN_LIFETIME` or `DB_MAX_CONN_IDLE_TIME`. pgx health-checks idle connections every minute.
- Connections identify themselves with `application_name` `sms-api` or `sms-migrate`
  (visible in `pg_stat_activity`).
- `database.DB.InTx` runs a function in a transaction: commit on success, rollback on error or panic.
- `database.DB.InTenantTx` does the same for tenant-owned data: it validates the tenant ID (a non-nil
  RFC 9562 UUID) before any SQL, then sets `app.tenant_id` **transaction-locally**
  (`set_config(..., true)`) as the first statement. The setting ends with the transaction, so it never
  stays on a pooled connection; it is never set at session level. Every tenant-scoped query must use the
  `pgx.Tx` it receives (for sqlc: `sqlcgen.New(tx)`); a query through any other connection has no tenant
  context and Row-Level Security returns no tenant rows. No tenant-owned table exists yet.
- The API **never runs migrations**. Use `cmd/migrate`.

### Database roles (Phase 4 Group 1, owner decision RLS-4)

| Role | Used by | Attributes and privileges |
| ---- | ------- | ------------------------- |
| bootstrap superuser (`DB_USER` of the PostgreSQL container, `sms` locally) | role provisioning and test helpers only | Superuser. Never used by `api` or `migrate`. |
| `sms_migrator` | `migrate` | Owns the application tables. Not a superuser; no `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION`; no role memberships. Database: `CONNECT`. Schema `public`: `USAGE`, `CREATE`. Does not own the database or the schema. |
| `sms_app` | `api` | Owns nothing. Not a superuser; no `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION`; no role memberships. Database: `CONNECT` only (no `TEMPORARY`, no `CREATE`). Schema `public`: `USAGE` only. Table privileges are granted per table by the migration that creates it, never `TRUNCATE`. |

- **Provisioning:** [`internal/database/dbroles/provision.sql`](internal/database/dbroles/provision.sql), an
  idempotent script run by a superuser in the application database. It never drops a role or data, sets no
  password (the caller does), and fails without changing anything if it finds an unsafe state (memberships,
  an application role owning the database or a schema, objects in `public` owned by another role). Locally
  it runs from [`infra/local/postgres-init/10-sms-roles.sh`](../infra/local/postgres-init/10-sms-roles.sh)
  (fresh volumes automatically; existing volumes by the documented upgrade command, see
  [`infra/local/README.md`](../infra/local/README.md)). Production provisioning is **not** part of this group.
- **The API checks its role on every new connection** and refuses a role that is a superuser, has
  `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION`, is a member of another role, owns the database, a
  schema, a table or a function, may create schemas or objects, or has `TRUNCATE` on any table. At startup
  this is fatal (the API exits with the reasons); later, an unsafe connection is closed and `/readyz` fails.
- **`migrate` checks its role** before every command and refuses a superuser or a role with `BYPASSRLS`,
  `CREATEROLE`, `CREATEDB`, `REPLICATION` or role memberships, so tables are always owned by `sms_migrator`.
- Because tenant-owned tables will use `FORCE ROW LEVEL SECURITY`, the migration role (their owner, with
  `NOBYPASSRLS` by owner decision G1-9) is subject to their policies for its ordinary data queries; a test
  proves it. No role has a blanket RLS bypass. A future cross-tenant data migration needs a separately
  designed, controlled procedure, approved when it is needed.

### Liveness vs. readiness

| Endpoint | Question it answers | Depends on PostgreSQL? | Use it for |
| -------- | ------------------- | ---------------------- | ---------- |
| `GET /healthz` | Is the process alive and serving HTTP? | **No** | Restarting a hung process. A database outage must not restart the API. |
| `GET /readyz` | Can this instance serve requests now? | **Yes** (ping, 2 s timeout) | Routing traffic. `503` while starting, shutting down, or when PostgreSQL is unreachable. |

`/readyz` returns the same generic problem document for every failure. The cause (for example
`connection refused` or an authentication error) is logged server-side once when readiness starts failing
(`readiness check failed`) and once when it recovers (`readiness check recovered`); it is never returned
to the client. Under heavy load, a readiness ping waits for a free pool connection, so `/readyz` can
report `503` when the pool is exhausted.

| Listener | Endpoint | Behaviour |
| -------- | -------- | --------- |

| Application | `GET /readyz` | Readiness. `200 {"status":"ready"}` when both listeners are serving **and** PostgreSQL answers a ping within 2 s; otherwise `503` problem. |
| Metrics | `GET /metrics` | Prometheus exposition format. Not served on the application listener. |
| Application | `POST /v1/messages` | Accept one message (`202`; `Idempotency-Key` required). Permission `messages:send`. |
| Application | `GET /v1/messages/{message_id}` | Current status of one message of the caller's tenant (`404` otherwise). Permission `messages:read`. |
| Application | `GET /v1/messages` | The caller's messages, newest first, cursor pagination and filters. Permission `messages:read`. |
| Application | `POST`, `GET`, `DELETE /portal/v1/session` | Client portal sign-in (sets the session cookie), current session (user, organization, permissions, CSRF token), sign-out. |
| Application | `GET /portal/v1/sender-ids`, `POST /portal/v1/message-estimates` | The organization's approved sender IDs; encoding and segment estimate from the shared segmentation function. |
| Application | `GET`, `POST /portal/v1/messages`, `GET /portal/v1/messages/{message_id}` | Portal list, submission (same engine and idempotency as `/v1`) and detail with customer-visible status history. |
| Application | `GET`, `POST /portal/v1/api-keys`, `DELETE /portal/v1/api-keys/{api_key_id}` | Owners only: list the organization's API keys (metadata only), create one (the full key is in the `201` response only), revoke one (Phase 4 Group 4). |

The `/v1` endpoints follow [`contracts/openapi/public-api-v1.yaml`](../contracts/openapi/public-api-v1.yaml)
exactly. Not implemented (no decided values or features yet): rate limits (`429`), credit checks (`402`) and
suppression lists (`recipient-opted-out`).

Errors use RFC 9457 problem documents (`application/problem+json`) with type `about:blank`, the
HTTP status title, a fixed client-safe detail, and the request ID. Internal error text, panic values,
database errors, and stack traces are never returned. The public API's own problem types
(`https://api.example.invalid/problems/<slug>`, contract §5) are used by the `/v1` endpoints.

A recovered panic is logged as one `panic recovered` entry with the request ID, method, route, the
panic value's Go **type** (`panic_type`), and a stack of function names with `file:line` positions.
The raw panic value is **never logged**, because it may contain connection strings, credentials,
tokens, or personal data; the stack omits argument values for the same reason.

Security (Phase 4 Group 6; `api` only):

| Variable | Default | Rules |
| -------- | ------- | ----- |
| `TRUSTED_PROXIES` | **required in production**; elsewhere empty (none) | The actual IP addresses or CIDR prefixes of the reverse proxies or load balancers in front of the API (comma-separated, at most 64), or `none` when clients connect directly. | `TRUSTED_PROXIES_ALLOW_BROAD_RANGES` | `false` | `true` accepts entries broader than an IPv4 `/8` or an IPv6 `/32`; the API then logs a `SECURITY WARNING` naming them at every start. |
| `SIGNIN_FAILURE_LIMIT_IPV4` | `100` | 1–1000000 failed sign-ins per IPv4 address and window |
| `SIGNIN_FAILURE_LIMIT_IPV6_64` | `100` | 1–1000000 failed sign-ins per IPv6 `/64` and window |
| `SIGNIN_FAILURE_LIMIT_IPV6_48` | `500` | 1–1000000 failed sign-ins per IPv6 `/48` and window; at least the `/64` limit |
| `SIGNIN_FAILURE_WINDOW` | `15m` | 1m–24h |
| `SIGNIN_REQUEST_RATE` | `10` | sign-in requests per second per IPv4 address or IPv6 `/64` (token bucket refill), > 0 and ≤ 10000 |
| `SIGNIN_REQUEST_BURST` | `100` | 1–1000000 (token bucket capacity) |
| `PASSWORD_HASH_CONCURRENCY` | `4` | 1–256 Argon2id computations at once (memory: 19 MiB each) |
| `PASSWORD_HASH_QUEUE` | `32` | 0–100000 callers that may wait for a slot; more are refused at once (`503`) |
| `PASSWORD_HASH_MAX_WAIT` | `1s` | longest wait for a slot (at most 1m), then `503` |

**Sign-in limit defaults (owner decision, decision log §23).** They are initial, configurable values, not
measurements of real traffic; review them once real traffic is observed. 100 **failed** attempts per IPv4 address
or IPv6 `/64` in 15 minutes (500 per IPv6 `/48`) bound password guessing from one source to about 400 guesses an
hour across all accounts, while successful sign-ins use none of the budget, so the users of one office or carrier
NAT are not blocked by each other's sign-ins. The all-attempt token bucket (10 per second, burst 100) bounds the
request rate, and so the password-hashing work, one source can cause.

**Password-hashing defaults (measured here, not in production).** On the 4-vCPU development container used for
this group, Argon2id with the stored parameters (19 MiB, 2 iterations) ran at about 31 hashes per second with one
at a time, 58 per second with 4 at once and 69 per second with 8 (no further gain at 16). The default (4 at once,
32 waiting, at most 1 s) keeps the hashing memory at 76 MiB and the worst queue wait near half a second. **These
limits MUST be measured again on the production hardware before launch** (a production gate).

The `/readyz` ping timeout is fixed at 2 seconds (`httpserver.DefaultReadinessTimeout`).

The processes log only an explicit, non-sensitive startup summary (environment, log settings, listener
addresses, database host, port, name, TLS mode, and pool size) — never the environment wholesale, the
password, or a connection string. The password is held in a `config.Secret`, which prints and logs as
`[REDACTED]`.

## Messaging (Phase 4 Group 2)

**Flow.** `POST /v1/messages` authenticates the API key (the tenant comes from the key only), validates the
request against the contract, and in **one transaction in the tenant's context** stores the message, its body,
its dispatch job (the transactional outbox), its first history entry and its idempotency record. A `202` means
*stored*, nothing more. The `dispatcher` claims due jobs per tenant (`FOR UPDATE SKIP LOCKED` with a lease),
records a submission attempt **before** calling the provider, calls it outside any transaction, and records the
classified outcome. Receipts are stored as received in the platform-owned `provider_receipts` inbox (a receipt
carries only the provider's reference) and are matched inside each tenant's context against that tenant's own
attempts, then applied by precedence. Nothing crosses tenants; no role bypasses row-level security.

**Reliability rules.** Dispatch is at-least-once inside the platform, never exactly-once delivery. A message is
handed over again only after a definite "not sent" outcome. An uncertain outcome (timeout, adapter failure, a
dispatcher crash during the hand-off) becomes `submission_uncertain` and is **never resubmitted or failed
automatically** (D-095 interim rule). Duplicate receipts change nothing; a different final report is recorded
as a conflict and the message is flagged (`has_conflicting_reports`; D-098 is open). `delivered` is reported
only after a provider receipt was processed.

**Provider boundary.** `internal/messaging/provider` is the provisional interface every adapter implements:
`Submit` (classified outcome: accepted with a provider reference, rejected, not sent (retryable or not),
uncertain), `Capabilities` (unknown is the zero value and is never treated as support), and `Run` (normalized
receipts to a durable sink). The engine never names an adapter; `internal/messaging/providers` builds the one
selected by `SMS_PROVIDER`. A future direct telco adapter adds a package and a case there, with its own settings.

**Simulator scenarios** (by destination, synthetic numbers `+6390000000xx`; any other number behaves like `01`):

| Last digits | Behaviour | Resulting status |
| ----------- | --------- | ---------------- |
| `00`–`09` | accepted, one delivered receipt | `delivered` |
| `10` | rejected by the provider | `rejected` (`provider_rejected`) |
| `20` | not sent, retryable, every attempt | `failed` (`retries_exhausted`) |
| `25` | not sent, permanent | `failed` (`permanent_submission_error`) |
| `30` | uncertain (simulated timeout) | `submission_uncertain`, never resent |
| `40` / `41` | accepted, undelivered / expired receipt | `undelivered` |
| `50` | accepted, the same receipt twice | `delivered` (the duplicate changes nothing) |
| `60` | accepted, no receipt | `provider_accepted`, then `unknown` after `SIMULATOR_REPORT_WINDOW` |

**Local administration.** `smsctl` (development and test only; connects as `sms_app`) creates and activates
tenants, approves sender IDs, issues API keys (printed once), revokes them, and prints a message's internal
trace (history, attempts, receipts). With the Compose stack: `docker compose -f infra/local/compose.yaml run
--rm smsctl bootstrap --name "Demo Co" --sender-id EXAMPLECO` ([`infra/local/README.md`](../infra/local/README.md)).

## Client portal API (Phase 4 Group 3)

The `/portal/v1` endpoints follow [`contracts/openapi/portal-api-v1.yaml`](../contracts/openapi/portal-api-v1.yaml)
and serve only the platform's own client portal (decision log §20). They are separate from the public API: a
portal session never opens `/v1`, and an API key never opens `/portal/v1`.

- **Sign-in** (`internal/portal`): the normalized email is looked up in the platform-owned login directory
  (the one approved RLS guard exception, G3-1), which gives the tenant; everything else — the Argon2id hash, the
  role, the lockout state — is read inside that tenant's context. Unknown addresses, wrong passwords and locked
  accounts get the same `401` after the same hashing work. Five consecutive failures lock the account for 15
  minutes; an inactive tenant gets `403` and no session.
- **Sessions:** cookie `__Host-sms_session` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`), value
  `<tenant>.<session id>.<secret>`; only the SHA-256 hash of the secret is stored. A session ends after 30 minutes
  without a request, 12 hours after sign-in, at sign-out, or with `smsctl portal-user revoke-sessions`.
- **CSRF:** every `POST`/`DELETE` except sign-in needs the session's CSRF token in `X-CSRF-Token` (it is in the
  `GET /portal/v1/session` response and is derived from the cookie's secret, so it is never stored). Sign-in
  accepts only `application/json`.
- **Permissions:** Owner and Sender may read and send; Viewer may only read; only the Owner manages API keys
  (`api_keys:manage`, MVP-03) and reads the audit log (`audit_log:read`, Group 6). Checked by every handler; the tenant always comes from the session.
- **API keys** (Phase 4 Group 4, decision log §21): the portal calls the same `apikey.Service` as `smsctl` and the
  public API. Creating a key requires the owner's current password (`current_password`; `portal.Service.Reauthenticate`,
  owner decision G4-7): failures count toward the sign-in lockout and receive `403 reauthentication-failed`, and no
  key is created. Only the hash of a key's secret is stored; the full key is returned once (`Cache-Control: no-store`)
  and never logged, nor is the password. Revocation applies from the next public API request. Creation, failed
  confirmations and revocation are audited (below); the last use of each key is shown (below).
- **Messages:** submission calls the same `messaging.Service.Accept` as `POST /v1/messages` (same idempotency
  records, dispatcher, simulator and history). The detail view returns the customer-visible status history only.

### Security audit log (Phase 4 Group 6, decision log §23)

`internal/audit` records security events in a durable, append-only audit trail (owner decision G4-8). Ordinary
logs remain operational logging only.

| Event (`action`) | Outcomes recorded | Written by |
| ---------------- | ----------------- | ---------- |
| `portal.sign_in` | success (a session started), failure (wrong password, locked account), denied (organization not active) | `portal.Service.Login` |
| `portal.sign_out` | success | `portal.Service.Logout` |
| `portal.account_locked` | **enforced** (the platform applied a security control; actor `system`; details: `locked_until`). `enforced` is the outcome of this action only (a database check). | the failed sign-in or re-authentication that starts the lock |
| `api_key.create` | success (key name and scopes), failure (password confirmation failed), denied (role) | `apikey.Service.Create`, `portal.Service.Reauthenticate`, the portal handler |
| `api_key.revoke` | success, denied | `apikey.Service.Revoke`, the portal handler |
| `api_key.list`, `audit_log.list` | denied only | the portal handler |
| `portal_user.create`, `portal_user.unlock`, `portal_user.sessions_revoke` | success (actor `system`, details `via: smsctl`; creation also `role`) | `portal.Service.CreateUser`, `Unlock`, `RevokeUserSessions` (used by `smsctl`), in the same transaction as the change |
| `sender_id.approve` | success (actor `system`, details `sender_id` and `via: smsctl`; no target) — a new approval only; approving an already approved sender ID changes and records nothing | `messaging.Service.ApproveSenderID` (`smsctl sender-id approve` and `bootstrap`), in the same transaction as the approval |

**System actor.** Administration through `smsctl` is recorded with the actor `system` and `via: smsctl`: the tool
has no operator identity (it runs with the API's database credentials), so these events do not say which person
acted. Attributing an action to an operator needs authenticated, MFA-protected internal administrators (D-021).
**Not audited yet:** the `smsctl` tenant registry commands (`tenant create`, the activation in `tenant create` and
`bootstrap`, `tenant suspend`, `tenant reactivate`). They change a platform-owned table and need a platform
administration audit design (security baseline S-14); no workaround writes them to a tenant's log.

- **Tables.** `security_audit_events` is tenant-owned (forced RLS, the approved policy). Events that belong to no
  organization — a sign-in for an address that is not registered (the address is **not** stored), malformed
  sign-in input, and the first rate-limited sign-in of each source and window — go to `platform_security_events`,
  which has no tenant column and which the application can insert into but **not read**: no portal user sees them;
  database administrators do, until an approved internal administration function exists.
- **Same transaction.** A key's creation or revocation, a session's creation, a sign-out, and a failed attempt's
  count are committed together with their event. If the event cannot be written, the change is rolled back and the
  request fails with `500` instead of succeeding unaudited. Refusals (`denied`) are refused whether or not their
  event could be written; a write failure is logged as an error.
- **Deduplication (B2 fix).** A refused request (`denied`) is recorded once per user, action and five-minute
  interval, and an attempt on a locked account once per account, action and lock (sign-in and password
  confirmation separately). These events carry a `dedup_key` built from server-side values only; a unique index on
  `(tenant_id, dedup_key)` makes a repeat an `INSERT … ON CONFLICT DO NOTHING` that writes nothing. No existing event
  is modified and no auxiliary table exists, so the mechanism itself cannot be used to create records: one user can
  cause at most one refusal event per audited action and five minutes, and the number of users is set by
  administrators. Failed sign-ins of an existing account remain one event each, bounded by the account lockout
  (five per lock); unknown-account sign-ins are bounded by the failed-attempt budgets (below).
- **Contents.** UTC time (assigned by PostgreSQL), tenant, actor type and ID, action, target type and ID, outcome, request ID, client IP
  address, user agent (control characters removed, at most 256 characters) and fixed, non-secret details
  (`audit.Details`). Never passwords, session tokens, CSRF tokens, API keys or their hashes, authorization headers
  or message text.
- **Identity and time.** PostgreSQL assigns each event's `id` (`uuidv7()`) and `occurred_at` (`clock_timestamp()`,
  stored in UTC): `sms_app` has no `INSERT` privilege on either column, so the application cannot back-date an event
  or choose an existing event's ID, and an upsert onto an existing event is refused (no `UPDATE`). The tenant is
  checked by row-level security (`WITH CHECK`); the actor comes from the authenticated session.
- **Append-only.** `sms_app` has `INSERT` (and `SELECT` on its tenant's events) only: no `UPDATE`, `DELETE` or
  `TRUNCATE`. Triggers also reject `UPDATE`, `DELETE` and `TRUNCATE` by any role, including the table owner
  `sms_migrator`. These controls stop ordinary application modification. They are **not tamper-proof** and do not
  protect against a database superuser, or the table owner after disabling the triggers, who can still change or
  remove rows; no evidence kept inside this database (including a hash chain) could prove otherwise. Evidence that
  holds against a superuser needs an **external immutable export** or **externally anchored integrity evidence** —
  a production requirement (security baseline S-8), not implemented here.
- **Reading.** `GET /portal/v1/audit-events` (owners only, `audit_log:read`; filters `action`, `outcome`,
  `occurred_from`, `occurred_before`; cursor pages). Sender and Viewer receive `403`, and the refusal is recorded.
- **Retention.** No audit row is deleted automatically: the retention period is an open decision (S-4, §10.8).

### Sign-in limits (Phase 4 Group 6, decision log §23)

`internal/signinlimit` applies two layers to every portal sign-in request, per **source**, **before** any
credential is looked at; a refusal is `429 too-many-sign-in-attempts` with `Retry-After` (seconds, rounded up),
reveals nothing about any account, and never counts toward, starts or extends an account lock. The account lockout
(five failures, 15 minutes, G3-3) is unchanged and independent.

1. **All-attempt token bucket** per IPv4 address or IPv6 `/64` (`SIGNIN_REQUEST_RATE`, `SIGNIN_REQUEST_BURST`):
   every request takes a token, including malformed ones; an empty bucket refuses (`Retry-After` until the next
   token).
2. **Failed-attempt budgets** within `SIGNIN_FAILURE_WINDOW` (a fixed window from the first reservation): per IPv4
   address, per IPv6 `/64` and per IPv6 `/48` aggregate. Before the password is checked the attempt **reserves**
   one slot in each budget of its source (the `/32`, or the `/48` and the `/64`), all or none. A successful sign-in,
   and an attempt whose password was never checked (malformed request, `503`), **refunds exactly its own slots**;
   every earlier failure stays counted, so a valid account of the attacker's own resets nothing. Failures include
   wrong passwords, unknown addresses, locked accounts and organizations that are not active. Rotating IPv6
   addresses or `/64`s inside one `/48` is stopped by the `/48` aggregate.
3. **Bounded password hashing** (`PASSWORD_HASH_*`): at most `CONCURRENCY` Argon2id computations at once and at most
   `QUEUE` callers waiting, each for at most `MAX_WAIT`; beyond that the API answers `503 service-busy` with
   `Retry-After: 2` without checking the password (sign-in and API key creation). A distributed attack can still
   make the service busy; it cannot exhaust memory or CPU, and a `503` uses no failure budget.

- **Shared, atomic, durable.** `portal_sign_in_request_buckets` and `portal_sign_in_failure_budgets` (platform-owned,
  no tenant data) live in PostgreSQL, so every API instance shares them and a restart resets nothing. A token is
  taken by one atomic upsert; the budgets of an attempt are reserved in one transaction, always in the same order
  (`/48` before `/64`), each by an atomic upsert that serializes concurrent attempts on its row, and the transaction
  is rolled back when any budget would exceed its limit. Clock differences between instances cannot add tokens.
- **Cleanup.** Every API process runs a cleanup cycle at start and then every minute
  (`signinlimit.Limiter.Run`). A cycle deletes budgets whose window has ended and buckets that are full again, in
  batches of at most 1,000 rows, each batch its own short transaction, and at most 50 batches per table: at most
  50,000 rows per table, cycle and process, so a high-cardinality attack cannot make one cycle monopolize the
  database. Each batch chooses its rows with `FOR UPDATE SKIP LOCKED`: cleanup never waits for a row that a sign-in
  (or another process's cleanup) holds. It skips the row, and a later cycle takes it. A sign-in therefore cannot
  deadlock with cleanup. The former single `DELETE` locked rows in table order and could deadlock with a sign-in
  that locks an IPv6 `/48` before its `/64` (final review of PR #23; reproduced, and fixed with a regression test).
  Several processes share the work instead of contending for it. A batch is chosen through the `window_start_at`
  or `refilled_at` index and deleted through the primary key, so it costs the same however many rows wait.
- **Empty budgets.** A budget whose slots were all refunded (successful sign-ins) is **not** deleted early: it stays
  until its window ends, like any other. An empty budget and an absent one behave the same. Deleting empty budgets
  early would need an index on the counter, which every reservation and refund changes, making each of those
  updates a non-HOT update.
- **Correctness does not depend on cleanup.** An ended window restarts on its next reservation and a bucket's tokens
  are computed from the time, so a failed or skipped cycle only leaves rows in place.
- **Storage is not bounded by a fixed number.** The tables hold one bucket row per source seen within a refill time
  (10 s by default, longer for a source refused within the last five minutes) and one budget row per source with
  a reservation in an open window, plus up to one cleanup interval. A row is created by any request from a new
  source, without authentication, so the tables grow with the **rate of new source addresses** (IPv6 sources are
  plentiful). If new sources arrive faster than cleanup's work bound removes them, the backlog grows; the cycle is
  then reported as incomplete. Edge rate limiting (S-12) and monitoring of the metrics below are what bound it in
  production.
- **Metrics** (on the metrics listener, labels without addresses, users or tenants):
  `sms_signin_limit_cleanup_runs_total{result="success"|"failure"}` (their sum is the number of attempts),
  `sms_signin_limit_cleanup_incomplete_runs_total` (stopped at the work bound or failed, rows possibly left),
  `sms_signin_limit_cleanup_duration_seconds` (histogram), `sms_signin_limit_cleanup_deleted_rows_total{table}`
  (`failure_budgets`, `request_buckets`), and `sms_signin_limit_cleanup_last_success_timestamp_seconds` (0 until a
  cycle succeeds; a failed cycle never moves it). A failed cycle is logged as an error, and an incomplete one as a
  warning. The alert conditions production monitoring must configure are in the security baseline (§9.1).
- **Audit.** One platform event per refused budget and window, and per refusing bucket and five minutes; a flood
  cannot multiply audit writes.
- **Known limits.**
  - **Many networks.** An attacker holding many `/48`s (or many IPv4 addresses) gets a budget for each.
  - **No token bucket per `/48`.** Every `/64` of a `/48` has its own token bucket; only the failure budget is
    aggregated per `/48`.
  - **Valid accounts.** A successful sign-in returns its failure slots, so sign-ins with **valid credentials** (an
    attacker's own account, or several) are limited only by the token bucket of each source (10 per second). They
    can keep the shared password-hashing queue full from a few addresses. The bounded hasher protects memory and CPU,
    but other users then receive `503`. Hashing admission is first-come-first-served, not fair per source.
  - **Shared addresses.** Failures from one NAT address can exhaust its budget for everyone behind it. The budget size
    bounds this but does not prevent it.
  - **Shared pool.** In a load test on the 4-vCPU development container, a sign-in flood on the same host raised `/v1/messages`
    latency (p50 about 4 ms → about 80 ms) whether or not cleanup ran: the flood and the messages API share CPU and
    the database pool.

  Edge rate limiting or a WAF in front of the API, capacity measurements on production hardware, and an evaluation of
  per-`/48` request limits and fair hashing admission are production gates (security baseline S-12); no new
  threshold is set here.

### Client IP addresses

`middleware.ClientIP` determines the address used by the rate limit and the audit log. By default it is the
**direct peer** of the connection; `X-Forwarded-For` and similar headers are ignored. When the peer is listed in
`TRUSTED_PROXIES`, `X-Forwarded-For` is read from right to left, skipping trusted proxies, and the first other
address is the client (an address a client prepends itself is never reached). A forwarded header from a peer that
is not a configured proxy is never read. Behind a load balancer the proxies **must** be configured, or every client
appears to come from the proxy and shares one sign-in limit; in production the API therefore refuses to start
until `TRUSTED_PROXIES` is set explicitly (`none` when there is no proxy). `Forwarded`
and `X-Real-IP` are not used. The access log still records no IP address.

### API key last use (owner decision G4-6)

After a key has authenticated **and** been authorized for a public API request, `apikey.Service.RecordUse` stores
the time in `api_keys.last_used_at` (UTC) — at most once per key per minute: a conditional update skips the write
while the stored time is less than a minute old, also across API instances. The portal therefore shows a time that
can be up to a minute older than the key's latest request, and "Never used" for `null`. Invalid, revoked and
wrongly scoped requests, and keys of an inactive organization, never update it. A failure to record it is logged
and does not fail the request (the time is informational).

Portal users are created locally with `smsctl` (there is no registration endpoint):

```bash
smsctl portal-user create --tenant TENANT_ID --email owner@example.invalid --role owner          # prints a generated password once
printf '%s\n' 'a long password' | smsctl portal-user create --tenant TENANT_ID --email viewer@example.invalid --role viewer --password-stdin
smsctl portal-user list --tenant TENANT_ID
smsctl portal-user unlock --tenant TENANT_ID --email owner@example.invalid
smsctl portal-user revoke-sessions --tenant TENANT_ID --email owner@example.invalid
```

## Migrations

Migrations use [goose](https://github.com/pressly/goose) v3 (ADR-0014) and live in
[`migrations/`](migrations/) as plain SQL files:

- **Naming:** `<UTC timestamp YYYYMMDDHHMMSS>_<snake_case_description>.sql` (timestamps avoid numbering
  collisions between parallel agents; AGENTS.md §10.1). Each file has `-- +goose Up` and, where
  possible, `-- +goose Down` sections. A unit test enforces the naming.
- **Embedded:** the files are compiled into the `migrate` binary (`go:embed`), so it works from any
  directory.
- **Transactions:** each migration runs in its own transaction; a failure rolls that migration back and
  stops. Statements that cannot run in a transaction (for example `CREATE INDEX CONCURRENTLY`) need
  `-- +goose NO TRANSACTION` in that file.
- **Locking:** `migrate` takes a PostgreSQL session-level advisory lock, so two `migrate` processes never
  apply migrations at the same time; the second waits (retrying every 5 seconds, up to 5 minutes).
- **Ordering:** a migration older than the latest applied one is rejected (no out-of-order apply).
- **Version table:** goose records applied versions in `goose_db_version`.
- **Role:** `migrate` runs only as the migration role `sms_migrator` (see "Database roles"); every command
  is refused for a superuser, so all tables are owned by `sms_migrator`.
- **Never automatic:** the API does not migrate on startup. Run `migrate` explicitly.
- **Rollback fails closed:** `migrate down` runs only when **both** hold, and is refused otherwise
  before any connection is made (there is no override flag):
  - `APP_ENV` is set **explicitly** to `development` or `test`. A missing `APP_ENV` is refused (the
    general configuration would otherwise default it to `development`), and `APP_ENV=production` is
    refused: production migrations are forward-only (AGENTS.md §10.1); fix a mistake with a new
    migration.
  - `DB_HOST` is a **loopback IP address** (`127.0.0.1`, anything in `127.0.0.0/8`, or `::1`). Host
    names, including `localhost`, and every non-loopback address are refused, so a rollback can only
    reach a local database.

  `up`, `status`, and `version` are not affected by these rules.

Migrations today:

| File | Content | Retention class |
| ---- | ------- | --------------- |
| `20261125041208_baseline.sql` | No SQL (goose needs at least one migration); creates only goose's version table | — |
| `20261126175603_create_tenants.sql` | The platform-owned tenant registry `tenants` (UUIDv7 `id` from PostgreSQL 18's `uuidv7()`, `display_name`, `status`, timestamps) and the `sms_app` grants | *account* (period undefined, subject to legal review) |
| `20261127150000_create_messaging.sql` | API keys, approved sender IDs, messages and their bodies, idempotency records, dispatch jobs, submission attempts, status history, the platform-owned receipt inbox and correlated receipts; forced RLS with the approved policy on every tenant table; column-level `sms_app` grants (no `DELETE` or `TRUNCATE`) | Per table, in the migration header (account, message metadata, message content, operational); periods undefined |
| `20261127200000_create_portal_accounts.sql` | Portal users (Argon2id hash, role, lockout state), server-side sessions (secret hash only) and the platform-owned login directory (email → tenant and user; the approved RLS guard exception G3-1); forced RLS on the tenant tables; column-level `sms_app` grants (no `DELETE` or `TRUNCATE`) | account (users, directory), operational (sessions); periods undefined |

`tenants` has no `tenant_id` and no RLS policy: it is the global list of tenants, not data belonging to one.
The application role may read it, insert only `display_name`, and update only `status` and `updated_at`.
Its `Down` section drops the table (local development and tests only; production is forward-only).

Commands (run from `backend/` with the `DB_*` variables set; see "Running locally"):

| Command | Effect |
| ------- | ------ |
| `go run ./cmd/migrate up` | Apply all pending migrations, print each result and the new version. |
| `go run ./cmd/migrate status` | List every migration with `applied`/`pending` and its time. |
| `go run ./cmd/migrate version` | Print the current version (`0` if none applied). |
| `go run ./cmd/migrate down` | **Rollback:** undo the most recent migration. Requires an explicit `APP_ENV=development` or `test` and a loopback-IP `DB_HOST` (see above). Run it repeatedly to go further back. |

Exit codes: `0` success, `1` failure (message on stderr), `2` usage error.

## sqlc

[`sqlc.yaml`](sqlc.yaml) compiles SQL in [`queries/`](queries/) against the schema in `migrations/` into
the dedicated package `internal/database/sqlcgen` (pgx/v5 driver; no ORM). Conventions: no JSON tags on
database models, no generated interfaces, nullable columns as Go pointers, `timestamptz` as `time.Time`,
empty slices instead of nil.

The sqlc version (v1.31.1) is locked in [`tools/go.mod`](tools/go.mod), next to oapi-codegen. Regenerate from
`backend/` after changing a query, a migration or `sqlc.yaml`, and commit the result:

```powershell
go generate ./internal/database/...
```

The command is the same in PowerShell and in a Linux or macOS shell. sqlc v1.31.1 builds **without cgo** (it
parses SQL with a WebAssembly build of the PostgreSQL parser), so no C compiler is needed. The first run
compiles sqlc, which takes about half a minute.

**Never edit `internal/database/sqlcgen` by hand.** CI deletes the package, regenerates it, and fails on any
difference, extra or missing file, or non-deterministic output; the Windows job runs the same command.

## OpenAPI code generation (public API v1)

The public API contract [`contracts/openapi/public-api-v1.yaml`](../contracts/openapi/public-api-v1.yaml)
is the source of truth (ADR-0015). Go types and Chi routes are **generated** from it by
[oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) into the package
[`internal/publicapi`](internal/publicapi/) (owner decisions D1–D7, Phase 3 Group 4;
[decision log §9](../docs/engineering/decision-log.md#9-owner-decisions--go-contract-integration-phase-3-group-4-2026-11-25)).

| File | Role |
| ---- | ---- |
| `internal/publicapi/publicapi.gen.go` | **Generated. Never edit by hand.** Models, Chi routes with parameter binding, and the typed ("strict") request/response interface |
| `internal/publicapi/oapi-codegen.yaml` | Generator configuration (`models`, `chi-server`, `strict-server`) |
| `internal/publicapi/generate.go` | The `go:generate` directive |
| `internal/publicapi/publicapi_test.go` | Hand-written tests of the generated types |
| `tools/go.mod`, `tools/go.sum` | A separate module that locks oapi-codegen **v2.8.2** and all its dependencies by checksum, so they never enter the API module or the `api` binary |

The generated code needs one library at run time: `github.com/oapi-codegen/runtime` **v1.9.0** (in `go.mod`).

**Regenerate** after any change to the specification or the configuration, from `backend/`. The same
command works in Linux and macOS shells and in Windows PowerShell or `cmd` (it uses only the Go tool and
forward-slash relative paths):

```bash
go generate ./internal/publicapi/...
```

Then run `go test ./...` and commit the regenerated file together with the change that caused it. Never
fix generated code by editing it: change the specification (through its own review) or the configuration.
CI regenerates the code twice and fails if the result differs from the committed file or between runs
(step "Check generated code is up to date" in the **Go test and build** job; also run on Windows in the
**Go generate check (Windows)** job).

**What is generated, and what is not.** The generated layer routes requests, **binds** path, query and
header parameters to their declared Go types (a value that cannot be parsed, such as `limit=ten`, gives a
`400 validation-error`), reports a missing `Idempotency-Key` (`400 idempotency-key-missing`), and decodes
JSON bodies (invalid JSON gives `400 malformed-request`). It does **not** perform full OpenAPI request
validation — patterns, lengths, ranges, enum membership, required body fields, `additionalProperties:
false`, rejecting `null` where the contract does not allow it, `Content-Type` — and it does **not**
authenticate or authorize. Both are deferred to the first endpoint implementation (owner decision D6).
`TestPublicAPIBindingIsNotValidation` documents exactly which invalid requests still reach a handler.

**Absent, null, and value.** Response fields that the contract makes required and nullable
(`Message.client_reference`, `Message.status_reason`, `MessageList.next_cursor`) are Go pointers without
`omitempty`: they are always present, `null` when nil. Optional fields (`MessageCreateRequest.client_reference`,
optional `Problem` members, query parameters) are pointers with `omitempty`: absent is `nil`, never a zero
value. Go's JSON decoder also turns an explicit `null` into `nil`; rejecting `null` where the contract
forbids it is part of the deferred validation.

**Not mounted in production.** `httpserver.NewRouter` does not register any `/v1` route, so `/v1/*` still
returns the existing `404` problem (owner decision D4). `httpserver.mountPublicAPI` is the integration
point for the first endpoint implementation; today only tests call it. It always replaces the generator's
default error handlers, which would otherwise return raw Go error text as `text/plain`.

**Dependency updates.** Change the generator version only with owner approval, in `tools/`:
`go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@<version>`, then `go mod tidy`,
regenerate, and review the diff. `tools/go.mod` also raises `github.com/getkin/kin-openapi` (the
generator's spec parser) to v0.149.0, the first release fixing GO-2026-6789, GO-2026-6795, GO-2026-6800 and
GO-2026-6785 (owner decision, PR #8 review); generated output is byte-identical. Remove that line when the
generator itself requires a fixed version.

## Running locally

There are two ways to run the backend locally:

| | Docker Compose stack (Group 6) | Native (`go run`) |
| - | ------------------------------ | ----------------- |
| Start | `docker compose -f infra/local/compose.yaml up -d --build --wait` (from the repository root) | Start only PostgreSQL in Compose, then `go run ./cmd/migrate up` and `go run ./cmd/api` |
| Needs | Docker with Compose v2.7.0 or later | Go, plus Docker for PostgreSQL |
| Migrations | Automatic: the one-off `migrate` service runs `up` before the API starts | Explicit `go run ./cmd/migrate up` |
| Rollback (`migrate down`) | Not available (refused: `DB_HOST` is not a loopback IP) | Yes |
| Metrics (`:9090`) | Not reachable (inside the container only) | `http://127.0.0.1:9090/metrics` |
| Best for | Running the whole stack, the client portal, reviews | Changing and debugging Go code, rollback, metrics, integration tests |

The Compose stack is documented in [`infra/local/README.md`](../infra/local/README.md): one-command start,
health checks, migration lifecycle, reset, cleanup and troubleshooting. The image is built from
[`infra/docker/backend.Dockerfile`](../infra/docker/backend.Dockerfile):
- **Build:** a Go 1.27.4 builder; static binaries (`CGO_ENABLED=0`, `-trimpath`).
- **Runtime:** a distroless base, user 65532. No shell; both base images pinned by tag and digest.
- **Contents:** `api` (the entrypoint), `migrate`, and `healthcheck`.

`cmd/healthcheck` exists because the runtime image has no `curl`. It uses only the standard library and
accepts only `http` URLs whose host is a loopback IP. It follows no redirects and gives up after 3 s.
Its exit code:
- `0` when `/readyz` answers 200;
- `1` when the API is not ready or unreachable;
- `2` on a usage error.

The rest of this section describes the native way.

**3. Configure the Go application** for this PowerShell session by loading the same `.env` file (this also
sets `DB_MIGRATOR_PASSWORD` and `DB_APP_PASSWORD`):

```powershell
Get-Content infra/local/.env | Where-Object { $_ -match '^\s*[A-Z_][A-Z0-9_]*=' } | ForEach-Object {
    $name, $value = $_ -split '=', 2
    Set-Item -Path "Env:$($name.Trim())" -Value $value
}
$env:DB_HOST = "127.0.0.1"
$env:APP_ENV = "development"
```

The variables last until you close the window. Setting `APP_ENV` explicitly matters: `migrate down`
(step 9) is refused without it. Use the IP address `127.0.0.1`, not `localhost`: rollback and the
integration tests accept only a loopback IP. Other settings (`DB_SSLMODE`, pool sizes, …) use their
defaults; see "Configuration".

**4. Run migrations** as the migration role (`migrate` refuses the bootstrap superuser):

```powershell
cd backend
$env:DB_USER = "sms_migrator"; $env:DB_PASSWORD = $env:DB_MIGRATOR_PASSWORD
go run ./cmd/migrate up
go run ./cmd/migrate status
```

**5. Start the API** as the application role (Ctrl+C stops it gracefully; the API refuses any other role):

```powershell
$env:DB_USER = "sms_app"; $env:DB_PASSWORD = $env:DB_APP_PASSWORD
go run ./cmd/api
```

**6. Test readiness** in a second PowerShell window:

```powershell
Invoke-RestMethod http://127.0.0.1:8080/healthz      # status: ok
Invoke-RestMethod http://127.0.0.1:8080/readyz       # status: ready
```

With PostgreSQL stopped (step 8), `/readyz` returns `503`:

```powershell
try { Invoke-RestMethod http://127.0.0.1:8080/readyz } catch { $_.Exception.Response.StatusCode.value__ }
```

**7. Run the integration tests** (needs steps 1–3 in this window; from `backend/`). They require
`APP_ENV=test` and refuse to run otherwise. They connect as the **bootstrap superuser** (`DB_USER` and
`DB_PASSWORD` from `.env`, to create throwaway databases) and as the two roles (`DB_MIGRATOR_PASSWORD`,
`DB_APP_PASSWORD`), so repeat step 3 first if you changed `DB_USER` in steps 4–5:

```powershell
$env:APP_ENV = "test"
go test -tags integration ./...
$env:APP_ENV = "development"    # back to development for running the API and migrate down
```

**8. Stop PostgreSQL** (keeps your data; from the repository root):

```powershell
docker compose -f infra/local/compose.yaml stop
```

**9. Reset the local database.** To re-run migrations without deleting the database (needs
`APP_ENV=development` and `DB_HOST=127.0.0.1` from step 3; otherwise `down` is refused):

```powershell
$env:DB_USER = "sms_migrator"; $env:DB_PASSWORD = $env:DB_MIGRATOR_PASSWORD
go run ./cmd/migrate down       # repeat until "database version: 0"
go run ./cmd/migrate up
```

> **WARNING — the next command permanently deletes ALL data in your local database** (it removes the
> Docker volume `sms-local_postgres-data`). It affects only this local Compose project. Use it only when
> you want a completely empty database.

```powershell
docker compose -f infra/local/compose.yaml down -v
docker compose -f infra/local/compose.yaml up -d --wait
```

## Testing

| Kind | Command (from `backend/`) | Needs PostgreSQL? |
| ---- | ------------------------- | ----------------- |
| Unit tests | `go test ./...` | No |
| Unit + integration tests | `APP_ENV=test go test -tags integration ./...` | Yes (`APP_ENV=test`, loopback `DB_HOST`, `DB_*` set: `DB_USER`/`DB_PASSWORD` of the bootstrap superuser, plus `DB_MIGRATOR_PASSWORD` and `DB_APP_PASSWORD`) |

- **Unit tests** use fakes and in-memory listeners only; they never read the process environment or need
  Docker.
- **Integration tests** are the files ending in `_integration_test.go`, compiled only with the
  `integration` build tag. They connect with the `DB_*` variables, but **never use or modify `DB_NAME`
  itself**: every test creates its own empty database `sms_test_<random>` and drops it in cleanup, even
  when the test fails. Your local `sms` database and its data are never touched.
- **Safeguards (fail closed).** Because the tests create and drop databases, `internal/database/dbtest`
  refuses to start unless **all** of these hold, and fails the test with a setup message (never
  containing the password):
  - `APP_ENV=test` is set explicitly — missing, `development`, `production`, or any other value is refused;
  - the `DB_*` configuration is valid (for example, `DB_PASSWORD` is set);
  - `DB_HOST` is a **loopback IP address** (`127.0.0.1` or `::1`) — host names, including `localhost`,
    and non-loopback addresses are refused.

  Only generated `sms_test_<16 hex>` names are ever created or dropped, and never the configured
  `DB_NAME`, even if it starts with `sms_test_`. The tests are not silently skipped when the setup is wrong.
- **Roles in tests.** Every test database is provisioned with the same script as the local stack
  (`dbroles.ProvisionSQL`). If `sms_migrator` or `sms_app` does not exist on the server yet, it is created
  without a password. Tests that log in as a role read its password from `DB_MIGRATOR_PASSWORD` or
  `DB_APP_PASSWORD` and fail with setup instructions if it is missing. **Tests never change a role's
  password or attributes**, because the server may be your local Compose stack: the passwords are set by
  the provisioning script (`infra/local/postgres-init/10-sms-roles.sh`; in CI, the "Provision database
  roles" step). Use the values from `infra/local/.env`.
- Integration tests cover: connecting and pinging (PostgreSQL 18 verified), wrong password and missing
  database errors (without leaking the password), pool limits and closing, transaction commit and
  rollback, migrations (up, status, down, idempotency, failure rollback, the advisory lock, the exact
  list of tables and their owner), `/readyz` with the database available and unavailable, and the
  `migrate` command end to end (as `sms_migrator`; refused as the superuser).
- **Phase 4 Group 1** adds: the roles' attributes, memberships, ownership and exact privileges; everything
  `sms_app` must not do (create tables, views, functions, schemas or temporary tables; truncate; delete;
  choose a tenant's ID or status; read goose's table; `SET ROLE`); the API's and `migrate`'s role checks,
  including privileges granted later; provisioning on a fresh database, run again (idempotent), on a
  database created before role separation (upgrade without data loss), and refusing unsafe states; the
  tenant-context helper (invalid IDs rejected before SQL; the setting cleared after commit, rollback,
  statement error and panic; no leak across reused or concurrent connections; Row-Level Security enforced
  on a test-only table); UUIDv7 generation by PostgreSQL 18 (version 7, time-ordered); the tenant
  repository (lifecycle, invalid transitions, concurrency, pagination, validation); and the RLS catalog
  guard (passes on the migrated schema; detects deliberately unprotected tables).
- CI runs both, against a PostgreSQL 18.7 service container provisioned with the role script, plus
  smoke tests of the built binaries: `migrate` as `sms_migrator` (and refused as the superuser), the API as
  `sms_app` (and refused as the superuser and as `sms_migrator`).
- **RLS evaluation tests** (`internal/database/rlseval/`, Phase 3 Group 7) are the evidence for the
  owner's Row-Level Security decision ([RLS evaluation](../docs/architecture/rls-evaluation.md); ADR-0010
  accepted 2026-11-26); they are not product code. They create server-wide NOLOGIN roles, so they need the build tags
  `integration,rlseval`, `RLS_EVAL_DISPOSABLE_SERVER=1` and a never-migrated maintenance database, and they
  are **never** run against the Compose stack's database. Run them with `bash scripts/rls-evaluation.sh`
  from the repository root: it starts and removes its own disposable PostgreSQL container. CI runs them
  against its ephemeral service container. `RUN_BENCHMARKS=1` adds the manual, indicative benchmark.

## Checks (same commands as CI)

Run from `backend/`. CI uses the pinned versions below (see `.github/workflows/backend-ci.yml`).

```bash
gofmt -l .                                   # must print nothing
go vet ./... && go vet -tags integration ./... && go vet -tags integration,rlseval ./...
go test ./...
go test -race ./...                          # needs a C compiler (cgo); on Windows, run in CI or WSL
APP_ENV=test go test -tags integration -race ./...   # needs local PostgreSQL and the DB_* variables
bash ../scripts/rls-evaluation.sh                     # RLS evaluation tests; needs Docker (own disposable server)
go build -o bin/api ./cmd/api && go build -o bin/migrate ./cmd/migrate
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0 run ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.10.0 ./...
```

`govulncheck` analyses the standard library of the `go` found on your `PATH`, so run it with Go 1.27.4
itself on `PATH` (as CI does). If your `PATH` points to an older Go that only delegates to 1.27.4,
govulncheck reports type errors in the standard library rather than results.
